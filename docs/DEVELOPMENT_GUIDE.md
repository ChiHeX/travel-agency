# Travel Agency 开发规范

> 本文档适用于 `travel-agency` 全体成员。
> 目标是保证多人开发时接口统一、数据真实、代码可联调、可维护。
> HTTP API 的全局规范维护在 [API 契约](API.md)，模块级精确定义维护在 [OpenAPI 定义](openapi.yaml)。

## 1. 基本原则

1.  **禁止用死数据代替正式功能。**
    线路、团期、订单、库存、支付、退款、评价、统计等业务数据必须来自后端和数据库。
2.  页面硬编码、静态数组等脱离契约的临时 Mock 仅允许用于短期原型，合并到 `dev` 前必须移除。由 [OpenAPI 定义](openapi.yaml) 生成的契约 Mock 可以作为开发工具保留，但不得进入生产环境，也不得被描述为真实业务实现。
3.  前端与后端统一通过符合 [API 契约](API.md) 的 HTTP API 协作，前端不得直接依赖数据库结构。
4.  开发前先理解已有代码和接口，禁止为了"快速完成"重复实现已有模块或绕过现有架构。
5.  功能完成的标准是**真实业务链路可运行**，而不是页面能显示或接口简单返回 `200`。

正式业务链路应为：

``` text
Frontend → API → Controller → Service → Mapper → MySQL
```

## 2. 前后端接口规范

所有接口遵循 [API 契约](API.md) 的全局规则；每个模块的 HTTP Method、URL、请求与响应结构、字段类型、分页、状态码和认证授权以 [OpenAPI 定义](openapi.yaml) 为准。

前后端共同开发功能前，应先评审并冻结对应 OpenAPI 契约。前端可先使用契约 Mock 开发，后端必须直接按该契约实现；进入联调后，任何变更都必须按 [API 契约](API.md) 的流程同步受影响成员和调用方。本文档不重复字段表，避免形成多个不一致的规范来源。

## 3. 后端规范

后端原则上遵循：

``` text
Controller → Service → Mapper → Database
```

-   `Controller`：接收请求、参数校验、调用 Service、返回响应。
-   `Service`：业务规则、事务、状态变化和业务编排。
-   `Mapper`：数据库访问。
-   Controller 不得直接堆积复杂业务或绕过 Service 操作数据库。
-   请求和响应模型遵循 [API 契约](API.md)，根据需要使用 DTO / VO，不应无条件直接暴露数据库 Entity。
-   金额统一使用 `BigDecimal`，不得使用 `float` / `double`
    处理业务金额。
-   关键参数、权限和业务条件必须由后端再次校验，不能信任前端。
-   涉及订单、名额、支付、退款等多表一致性的操作必须正确使用事务。

## 4. 前端规范

前端按职责组织代码：

``` text
views/       页面
components/  可复用组件
api/         后端接口
stores/      Pinia 状态
router/      路由
utils/       通用工具
```

-   API 调用集中放在 `src/api/`，并遵循 [API 契约](API.md)；禁止在多个页面重复拼接相同请求。
-   页面必须正确处理 Loading、空数据和请求失败。
-   前端可以进行展示性校验，但不能承担最终业务校验。
-   订单金额、剩余名额、订单状态、支付结果、退款资格、评价资格和用户权限等关键结果以后端为准。
-   禁止为了页面"看起来完整"自动生成虚假的订单、销量、评价或统计数据。

## 5. 数据与数据库规范

测试和演示数据应通过：

``` text
sql/test-data.sql
```

等统一初始化方式维护，并能够被后端真实查询。

正式数据库结构维护在：

``` text
sql/schema.sql
```

禁止只在个人数据库中手动修改表结构而不提交对应 SQL。

数据库结构变化时，应同步检查：

``` text
SQL → Entity / Mapper → Service → DTO / VO → API → Frontend
```

其中对外 API 的变化必须同步到 [API 契约](API.md)。

没有真实数据时应正常显示空状态，**真实空数据优于伪造数据**。

## 6. 核心业务约束

以下规则必须由后端保证：

-   `Route` 是可复用旅游线路，`Departure`
    是具体出发团期，订单必须关联具体团期。
-   创建订单时保存必要的价格和业务快照，历史订单不能使用当前价格重新计算。
-   创建订单时后端必须重新校验并可靠扣减团期名额，防止超卖。
-   订单状态只能按照服务端业务规则变化，前端不得直接决定最终状态。
-   支付成功不能仅依据浏览器跳转判断，支付宝沙箱回调必须由后端验证处理。
-   退款按照"申请 → 审核 → 处理 → 完成/拒绝"的服务端流程执行。
-   评价资格必须由后端验证。
-   权限必须由后端实施真实 RBAC 校验，隐藏前端按钮不能代替权限控制。

## 7. 安全规范

-   密码必须安全哈希保存，不得明文存储或返回前端。
-   身份证件等敏感信息应最小收集、最小展示并进行必要脱敏。
-   密码、Token、JWT 密钥、支付宝私钥、API 密钥等不得提交到 Git。
-   日志不得记录密码、完整身份证号、Token、私钥等敏感信息。
-   后端不得把完整异常堆栈直接返回前端。

## 8. 编码规范

开始开发前应阅读：

``` text
CONTRIBUTING.md
docs/DEVELOPMENT_GUIDE.md
docs/API.md（涉及接口设计或调用时）
docs/openapi.yaml（涉及具体接口、模块实现或联调时）
```

必须遵守以下规则：

1.  不得用硬编码或静态数组冒充已经完成的正式业务功能。
2.  缺少 API 时，应先在 [OpenAPI 定义](openapi.yaml) 中补全并评审契约；前端可使用契约 Mock 继续开发，后端随后按同一契约实现，不得在正式页面中长期维护自定义假数据。
3.  不得绕过现有 Controller / Service / Mapper，以及 [API 契约](API.md) 规定的认证和统一响应机制。
4.  不得为了当前任务创建与已有模块重复的数据模型、接口或工具。
5.  修改公共 API 时必须遵循 [API 契约](API.md) 的变更流程；修改数据库 Schema、枚举、权限规则等共享契约前也必须检查影响范围。
6.  如果任务只要求 UI
    或原型，应明确其尚未接入真实业务，不得将其描述为完整功能。
7.  修改完成后应验证相关前端、后端或数据库链路，而不是只检查生成的代码是否存在。

## 9. 功能完成标准

一个功能只有在与其范围相关的以下条件满足后，才可认为完成：

-   [ ] 符合项目现有架构和命名规范；
-   [ ] 正式业务不存在用于冒充真实实现的硬编码数据；
-   [ ] 数据库变更已同步到项目 SQL；
-   [ ] 后端接口真实可调用；
-   [ ] 前端通过统一 API 接入；
-   [ ] 请求、响应字段与 [API 契约](API.md) 一致；
-   [ ] 空数据、错误情况有合理处理；
-   [ ] 权限和关键业务规则由后端保证；
-   [ ] 不包含页面硬编码 Mock、调试代码或秘密信息；契约 Mock 仅作为开发工具；
-   [ ] 已完成必要的构建、测试和前后端联调。

## 10. 最终要求

> **真实数据优先于演示假数据。**\
> **稳定接口优先于临时拼接。**\
> **共享规范优先于个人习惯。**\
> **前后端通过明确的 [API 契约](API.md) 协作，后端负责最终业务正确性和安全性。**

任何成员编写的代码，都应保证其他成员能够继续调用、联调、测试和维护。
